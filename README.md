# lab1_wakeword — Wake Word / Keyword Spotting on STM32F407

Bare-metal STM32F407 Discovery firmware that listens continuously via the
onboard PDM microphone, computes an STFT spectrogram, runs a small CNN via
[ExecuTorch](https://pytorch.org/executorch/), and reports the predicted
spoken command over UART. This is a PyTorch/ExecuTorch port of TensorFlow's
[simple_audio](https://www.tensorflow.org/tutorials/audio/simple_audio)
keyword-spotting tutorial, adapted for a 1MB-flash microcontroller target.

`src/main.cpp` contains a clearly marked `STUDENT SECTION` and a few other
`TODO(student)` spots — the inference loop, the ExecuTorch bring-up, and the
memory-pool sizing — that's the actual assignment; everything else (mic
driver, spectrogram module, linker/startup/build config) is provided. Related
documents in this repo:

- `README-training-parameters.md` — the training-side task specification
  (dataset, feature extraction, model classes, export). This is not
  optional background reading: it's what you implement against for Task 1
  below.
- `README-testing.md` — environment setup and how to build/flash/run the
  firmware on host, hardware, and Renode, plus GDB debugging.
- `README-submission-instructions.md` — exactly what to submit, per-file
  format, and what the grader checks about each file.
- "Tasks", "Grading rubric" below — what you need to build and how it's
  scored.

## Architecture

```
PDM mic --(I2S2/DMA, pdm_mic.c)--> 16kHz int16 ring buffer
    --(src/spectrogram.c)--> (49,128) normalized STFT-magnitude features
    --(ExecuTorch, ImprovedKWSNet)--> 4-way logits
    --(UART, 115200 8N1)--> "PREDICTION: <label> conf=<float>\r\n"
```

- **Mic driver** (`pdm_mic.c`/`pdm_mic.h`, real hardware; `synthetic_mic.c`,
  Renode): referenced via relative path from
  `../stm32f4_audio_examples/audio_in_to_wav/src/` — not forked here. See
  that file's "Windowing model" doc comment for the ring-buffer API.
- **Spectrogram** (`src/spectrogram.c`/`.h`): provided, STFT magnitude only
  (no MFCC, no mel filterbank) — see `spectrogram.h`'s doc comment for the
  exact algorithm and `README-training-parameters.md` for why it's
  structured this way. You'll need a matching Python implementation for
  training (`models/spectrogram_features.py`) — generate it with an AI
  coding assistant and numerically verify it against this C implementation,
  see `README-training-parameters.md` §2.
- **Model** (`ImprovedKWSNet`, class definition given in
  `README-training-parameters.md` Appendix A): you train it, export it to
  `submission/model.pte`, and it gets embedded into firmware at build time.
- **Firmware glue** (`src/main.cpp`): loads the model, sets up ExecuTorch
  memory pools, and — in the `STUDENT SECTION` and nearby `TODO` spots —
  runs the loop. See "Tasks" below.

## Tasks

Five things to build. See `README-submission-instructions.md` for exact
output formats and grading detail per file, and
`README-training-parameters.md`/`README-testing.md` for the "how".

1. **Train both models** (`ExactMatchCNN`, host-only reference;
   `ImprovedKWSNet`, what ships) — dataset loading and the training loop are
   your code; the model classes are given to you verbatim, and the
   spectrogram feature-extraction function is AI-generated by you and then
   numerically verified against the firmware's C implementation (not
   hand-derived — see `README-training-parameters.md` §2 for why). Full
   spec: `README-training-parameters.md`.
2. **Fill in `src/main.cpp`** — three spots, all `TODO(student)`-marked:
   - the ExecuTorch memory pool sizes (`method_pool`/`planned_pool`,
     [src/main.cpp:71-72](src/main.cpp#L71-L72), currently `0`/`0`);
   - the ExecuTorch bring-up block
     ([src/main.cpp:109-139](src/main.cpp#L109-L139)) — loading the
     `Program`, building the `MemoryManager`, calling `load_method`,
     currently commented pseudocode;
   - the `STUDENT SECTION` ([src/main.cpp:158-246](src/main.cpp#L158-L246))
     — a VAD (voice-activity-detection)-gated capture + inference loop,
     also pseudocode-commented with the exact steps and which provided
     functions/buffers to use.

   See `README-testing.md`'s "Memory budget" for how to size the pools
   instead of guessing, and "GDB / fault debugging" for chasing load/runtime
   failures.
3. **Instrument inference timing** — wrap spectrogram computation and
   `method.execute()` (inside the `STUDENT SECTION`) with `hal_ticks_ms()`.
4. **Capture VAD debug values** — under Renode + GDB, break right after your
   code prints `DETECTED` and read two values off. See
   `README-testing.md`'s "Testing with Renode" → "Reading debug values via
   GDB under Renode".
5. **Build and package your submission** — both firmware variants (real-mic
   and synthetic-mic/Renode), plus the operator-list and memory-usage
   reports. See `README-testing.md` for build commands and
   `README-submission-instructions.md` for exactly what's expected.

## Suggested steps

A reasonable order to tackle the tasks above in — not the only order that
works, but it avoids the most common rework (training against a
spectrogram implementation you haven't verified, or fighting Renode/GDB
before the host build even runs):

1. Read `README-training-parameters.md` start to finish before writing any
   training code.
2. Generate `models/spectrogram_features.py` with an AI coding assistant
   first (from the contract/algorithm spec in `README-training-parameters.md`
   §2), then verify it against the firmware's compiled C implementation
   (`README-testing.md`'s "Cross-checking the spectrogram") — expect to
   iterate, since a first attempt commonly gets a subtle convention wrong
   (§2's pitfalls), and a mismatch here silently invalidates everything
   trained against it.
3. Write your training script, train both models, and produce
   `submission/model.pte` plus a regenerated
   `src/spectrogram_norm_constants.h` (Task 1).
4. Build & validate on host (`README-testing.md`'s "Build / test on host")
   — this needs `src/main.cpp`'s ExecuTorch bring-up done (part of Task 2)
   but not the full `STUDENT SECTION` loop, and is much faster to iterate
   on than hardware or Renode.
5. Fill in the rest of `src/main.cpp` (memory pools, `STUDENT SECTION`),
   using the host build to sanity-check the model/spectrogram side stays
   correct as you go.
6. Build, flash, and test on real hardware; separately build for Renode
   (after regenerating the synthetic-mic buffer — see
   `README-submission-instructions.md`); instrument timing on both
   (Task 3).
7. Under Renode + GDB, capture your VAD debug values (Task 4).
8. Assemble `submission/` (see "Final file checklist" below), then
   self-grade before actually submitting (see "Grading rubric").

## Grading rubric

130 points total, 60% (78/130) to pass. Exact JSON formats and per-file
grading detail are in `README-submission-instructions.md`; this table is
the points breakdown:

| ID | What it checks | Format / threshold | Points |
|----|-----------------|---------------------|-------:|
| SHAPE | All required `submission/` files present, plus a `*.py`/`*.ipynb` under `models/` | presence only | 0 or 130 (gate) |
| F1 | `ops.json` matches `model.pte`'s actual operators | exact set match | 5 |
| M1 | `memory.json` matches `firmware_stm32.elf`'s measured sizes | exact match | 5 |
| B1 | `firmware_stm32_renode.elf` boots fault-free under Renode | CFSR == 0 | 5 |
| T1 (×6) | 6 individual real Speech Commands clips (3 "yes", 3 "no") | expected label among captured predictions | 10 each (60 total) |
| T2 | Concatenated 4-word sequence | both "yes" and "no" must appear, any order | 25 |
| T3 | 10 individual real-recorded clips (5 "yes", 5 "no") | 1 wrong free, then -0.5/each | 5 |
| T4 | Two 5-word real-recorded sequences (10 words total) | same 1-free/-0.5 tolerance | 5 |
| TIME1 | `timing.json` present, all 6 fields plausible | `0 < value < 30000` ms | 5 |
| DBG1 | `debug_values.json` present, self-consistent | both non-negative, `onset <= written` | 5 |
| ACC1 | `model_metrics.json` present, plausible | accuracies in `[0,1]`; `improved_val_accuracy >= 0.60`; counts positive ints | 5 |
| SZ1 | `improved_pte_bytes` matches submitted `model.pte`'s actual size | exact match | 5 |

**SHAPE is a gate** — miss any required file and the whole submission scores
0, so run through the "Final file checklist" above before grading yourself.
**F1, M1, and SZ1 are exact-matched** (properties of the files you actually
built/exported — always regenerate them from your real artifacts, never
hand-edit). Everything else is either a live behavioral test (T1-T4, B1) or
a plausibility check on self-reported numbers (TIME1, DBG1, ACC1). T3/T4 use
real (not training-set) recordings of an actual speaker/mic and are graded
more leniently than T1/T2 for exactly that reason — occasional misses on
real audio are expected, not a sign of a broken implementation.

Ask your instructor for the location of the autograder (`grade.py`) if you
want to self-grade before submitting — point it at your repo root, not
`submission/`; expect ~3.5-4 minutes end-to-end:

```bash
source <path-to-renode-venv>/bin/activate
python3 <path-to-autograder>/grade.py /path/to/your-repo
```
