# Submission instructions — wake-word/keyword-spotting lab

This document specifies exactly what your submission must contain: every
file you need to add or edit in this repo, its exact format (where one is
required), and what the grader checks about it. It assumes you've already
read `README.md` (the lab's tasks) and, for the training-side files,
`README-training-parameters.md`.

Everything is graded **in place in your cloned repo** — `grade.py` takes
the path to your repo, not a separate submission folder you assemble by
hand. Because this is a template repo cloned per student, your submission
*is* this repo: files that ship unchanged are submitted as-is, and the
sections below cover only the files you must add (`NEW`) or change
(`EDIT`) — everything else should be left alone.

For what each check is worth and the overall pass threshold, see
`README.md`'s "Grading rubric" — this document doesn't repeat that table,
only which rubric item(s) apply to each file below.

## src/main.cpp

`EDIT`. Three spots, all inside this one file: the ExecuTorch memory pool
sizes (`method_pool`/`planned_pool`, currently `[0]`/`[0]`), the ExecuTorch
bring-up block (loading the `Program`, building the `MemoryManager`, calling
`load_method`), and the `STUDENT SECTION` (the VAD-gated capture +
inference loop, including the `PREDICTION: %s conf=%f\r\n` UART output).
See `README.md`'s "Tasks" for what each spot needs to do and
`README-testing.md` for how to size the memory pools and debug load
failures.

This file itself is not copied into `submission/` and its source is never
read by the grader — but it's what makes `submission/firmware_stm32.elf`
and `submission/firmware_stm32_renode.elf` behave correctly, so its
correctness is checked indirectly through those two files: rubric items
**B1** (boots fault-free), **T1**/**T2**/**T3**/**T4** (correct
predictions), and **TIME1**/**DBG1** (only meaningful if your own
instrumentation and `DETECTED` print actually exist and are correct).

## src/generated/synthetic_audio_data.h

`NEW`, generated by a script (not hand-written). Regenerate it at **22
seconds** before building `firmware_stm32_renode.elf`:

```bash
python3 <path-to>/stm32f4_audio_examples/audio_in_to_wav/tools/wav_to_c_array.py \
  --output src/generated/synthetic_audio_data.h --seconds 22
```

Why 22s specifically: the grader's longest test fixtures are two ~20s,
5-word sequences (not one 10-word sequence) — `synthetic_audio_pcm` is
`const`, so its *declared* capacity costs real flash whether or not Renode
later overwrites its contents at runtime, and a buffer sized for all 10
words at once wouldn't fit in 1MB of flash alongside everything else. 22s
covers either 5-word fixture with margin. The shipped default (96,000
samples / 6s) is too small for these and will fail the affected checks if
you skip this step. This only affects the Renode build's compiled-in
array, not `firmware_stm32.elf` or your actual deployed (real-mic)
firmware.

**Grading**: not itself a submitted file and not directly checked, but
`firmware_stm32_renode.elf` will fail to run the longer fixtures correctly
without it — checked indirectly through **B1** and **T4**.

## submission/firmware_stm32*.elf

`NEW`, two files. **Why two**: Renode has no PDM microphone hardware model,
so it can only run the synthetic-mic build (`MIC_SOURCE=synthetic`, the
`stm32-renode` preset) — that's the one actually driven through the live
test clips (**B1**, **T1**-**T4**). The real-mic build (`MIC_SOURCE=real`,
the `stm32` preset) is what you'd actually flash to hardware, and its
memory footprint is what's checked (**M1**) — the two builds can differ
slightly in size since they link different mic driver source files.

```bash
cmake --preset stm32          && cmake --build --preset stm32
cp build/stm32/firmware.elf           submission/firmware_stm32.elf

# first regenerate src/generated/synthetic_audio_data.h at 22s -- see
# "src/generated/synthetic_audio_data.h" above
cmake --preset stm32-renode   && cmake --build --preset stm32-renode
cp build/stm32-renode/firmware.elf    submission/firmware_stm32_renode.elf
```

See `README-testing.md` for build/flash/Renode environment setup in
detail.

**Grading**: presence required (**SHAPE**). `firmware_stm32.elf` — rubric
**M1** (memory usage, 5 points). `firmware_stm32_renode.elf` — rubric
**B1** (boots fault-free, 5 points), **T1** (6 individual clips, 10 points
each, 60 total), **T2** (4-word sequence, 25 points), **T3** (10
real-recorded clips, 5 points, lenient tolerance), **T4** (two 5-word
real-recorded sequences, 5 points, same tolerance). These are live
behavioral tests driven through your actual firmware, not format checks —
see `README.md`'s "Grading rubric" for exact pass criteria per test.

## submission/ops.json

`NEW`. The operator list your exported model actually uses:

```json
{
  "ops": [
    "aten::_native_batch_norm_legit_no_training.out",
    "aten::addmm.out",
    "aten::convolution.out",
    "aten::mean.out",
    "aten::permute_copy.out",
    "aten::relu.out"
  ]
}
```

`export_to_executorch()`'s printed op list (`README-training-parameters.md`
Appendix A) is a **best-effort starting point** for rebuilding
ExecuTorch's kernel selection (`README-testing.md` → "Building/rebuilding
ExecuTorch") — it is explicitly *not* guaranteed to exactly match what your
compiled `.pte` records, since it's read from the pre-lowering graph. For
`ops.json`, get the exact, ground-truth list straight from your own
compiled `submission/model.pte` instead (requires the ExecuTorch venv
active):

```python
import json
import executorch.exir._serialize._program as program_mod

with open("submission/model.pte", "rb") as f:
    pte = program_mod.deserialize_pte_binary(f.read())

ops = set()
for plan in pte.program.execution_plan:
    for op in plan.operators:
        ops.add(f"{op.name}.{op.overload}" if op.overload else op.name)

print(json.dumps({"ops": sorted(ops)}, indent=2))
```

Copy that output directly into `ops.json`.

**Grading**: presence required (**SHAPE**). Rubric **F1** (5 points): the
grader independently re-runs this same deserialization against your
submitted `model.pte` and requires an **exact set match** — not a
guess-and-hope value, since it's read straight from the file you're
already submitting.

## submission/memory.json

`NEW`. Your firmware's measured flash/SRAM/CCM-RAM usage, from
`submission/firmware_stm32.elf`'s section headers:

```json
{
  "flash_bytes": 222329,
  "sram_bytes": 104432,
  "ccmram_bytes": 65160
}
```

Region boundaries follow the standard STM32F407 memory map: flash @
`0x08000000`/1MB, SRAM @ `0x20000000`/128KB, CCM RAM @ `0x10000000`/64KB.
Every *allocated* (`SHF_ALLOC`) section in the ELF counts toward whichever
region its address falls in; sections without that flag (`.debug_*`,
`.comment`, ...) occupy no space in the flashed image and don't count.
List sections with their addresses/sizes/flags via:

```bash
arm-none-eabi-readelf -S -W submission/firmware_stm32.elf
```

then sum the `Size` column per region by hand, or automate the same
bucketing:

```python
import json, re, subprocess

REGIONS = {
    "flash_bytes":  (0x08000000, 0x08000000 + 1024 * 1024),
    "sram_bytes":   (0x20000000, 0x20000000 + 128 * 1024),
    "ccmram_bytes": (0x10000000, 0x10000000 + 64 * 1024),
}
out = subprocess.check_output(
    ["arm-none-eabi-readelf", "-S", "-W", "submission/firmware_stm32.elf"], text=True)

totals = {k: 0 for k in REGIONS}
for line in out.splitlines():
    m = re.match(r"\s*\[\s*\d+\]\s+(\S+)\s+(\S+)\s+([0-9a-fA-F]+)\s+[0-9a-fA-F]+\s+"
                 r"([0-9a-fA-F]+)\s+[0-9a-fA-F]+\s+(\S*)", line)
    if not m:
        continue
    _name, _type, addr_s, size_s, flags = m.groups()
    size = int(size_s, 16)
    if "A" not in flags or size == 0:
        continue
    addr = int(addr_s, 16)
    for region, (lo, hi) in REGIONS.items():
        if lo <= addr < hi:
            totals[region] += size
            break

print(json.dumps(totals, indent=2))
```

**Grading**: presence required (**SHAPE**). Rubric **M1** (5 points): the
grader independently re-measures your submitted `firmware_stm32.elf` the
same way and requires an **exact match**.

## submission/timing.json

`NEW`. Milliseconds-per-inference (one pass through your `STUDENT SECTION`
loop's spectrogram-compute + `method.execute()` steps), measured with
`hal_ticks_ms()` — once on real hardware, once under Renode:

```json
{
  "board_spectrogram_ms": 180.0,
  "board_inference_ms": 950.0,
  "board_total_ms": 1130.0,
  "renode_spectrogram_ms": 4200.0,
  "renode_inference_ms": 21000.0,
  "renode_total_ms": 25200.0
}
```

Renode simulates CPU cycles rather than running at real wall-clock speed,
so its numbers will typically be much larger than the board's — expected,
not a bug.

**Grading**: presence required (**SHAPE**). Rubric **TIME1** (5 points,
plausibility-checked, not exact-matched): all 6 fields required, each a
positive number under 30000 (30s) — your numbers will legitimately differ
from anyone else's depending on your implementation.

## submission/debug_values.json

`NEW`. Two integers read via GDB, under Renode, at the moment your firmware
first detects speech (i.e. right after wherever your code prints
`DETECTED`) — the sample count your mic driver has written so far
(`pdm_mic_samples_written()`'s return value) and the sample index you
computed as the detected onset:

```json
{
  "written_at_first_detection": 8420,
  "onset_sample_at_first_detection": 8100
}
```

See `README-testing.md`'s "Testing with Renode" → "Reading debug values via
GDB under Renode" for the exact GDB session.

**Grading**: presence required (**SHAPE**). Rubric **DBG1** (5 points,
plausibility-checked, not exact-matched): both fields present and
non-negative integers, and `onset_sample_at_first_detection <=
written_at_first_detection` (you can't detect an onset later than the mic
has actually written up to) — your exact numbers depend on your own VAD
thresholds/algorithm.
